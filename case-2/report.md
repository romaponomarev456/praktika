# Отчёт: восстановление процесса обработки заявок на закупку

Журнал: `students.csv`, 1000 экземпляров (`ProcessInstanceId`), 6508 событий. Данные синтетические, реальных людей и документов не содержат.

## 1. Метод, группировка и инструменты

Инструмент — Python 3 + pandas (скрипт `analysis.py`, воспроизводим: `python analysis.py students.csv`). Дополнительно использован LLM (Claude) как ассистент для написания кода и формулировки гипотез; каждая гипотеза, выдвинутая с его помощью, проверена программно на полном журнале (см. раздел 6), а не принята на веру.

Шаги:

1. Загрузка CSV (`utf-8-sig`, т.к. файл с BOM), парсинг `Timestamp`.
2. Группировка строк по `ProcessInstanceId`.
3. Сортировка внутри группы по **числовому** `EventIndex` (явно приведено к `int64`, не лексикографически — проверено, что CSV уже даёт `int64` при чтении pandas).
4. Для каждого экземпляра построена цепочка `ActivityName` в порядке `EventIndex`.
5. Из каждой цепочки извлечены все пары соседних активностей (`zip(seq, seq[1:])`) — это и есть наблюдаемые переходы; подсчитана частота каждой уникальной пары.
6. Полные маршруты экземпляров (строка `" > ".join(chain)`) сгруппированы в таблицу вариантов.
7. Гипотезы о правилах ветвления (`Result`, порог `Amount`) проверены `assert`-ами на всех 1000 экземплярах — ни одного исключения не найдено (вывод скрипта: все проверки пройдены).

Глобальный порядок строк файла по времени не использовался для построения цепочек — только `EventIndex` внутри экземпляра, как указано в описании данных.

## 2. Активности, старт и окончания

Обнаружено 10 уникальных `ActivityName`. Каждый экземпляр начинается событием `process_started` с активностью **«Регистрация заявки»** (1000 из 1000, роль `system`) — альтернативных стартов нет.

Экземпляр всегда заканчивается событием `process_completed` на одной из трёх терминальных активностей:

| Финал | Количество | Доля |
|---|---|---|
| Заявка выполнена | 911 | 91,1% |
| Заявка отклонена | 63 | 6,3% |
| Заявка отменена | 26 | 2,6% |

Нетерминальные активности и роли исполнителей (из `Role`, однозначно привязаны к `ActivityName`):

| Активность | Роль | Тип |
|---|---|---|
| Первичная проверка | specialist | человеческое задание |
| Согласование руководителем | manager | человеческое задание |
| Доработка заявки | requester | человеческое задание |
| Проверка бюджета | finance | человеческое задание |
| Дополнительное согласование | director | человеческое задание |
| Исполнение закупки | procurement | человеческое задание |

Все человеческие завершения укладываются в рабочее время 09:00–18:00, Пн–Пт (проверено по `Timestamp`: часы 9–17, дни недели 0–4), что соответствует регламенту из `dataset_description.md`.

## 3. Основной маршрут, развилки, необязательные действия, возвраты

### Основной маршрут (магистраль)
Регистрация заявки → Первичная проверка → Согласование руководителем → Проверка бюджета → Исполнение закупки → Заявка выполнена.
Чистый вариант этого маршрута без доп. веток — 567 случаев (56,7%), пример `ProcessInstanceId = 00f3e3a0-9d7d-5eac-98a9-b605b6893e61` (Amount = 70 111.14).

### Развилка 1 — «Первичная проверка» (specialist)
- `Result = accept` → «Согласование руководителем» (1129 раз — больше 1000, т.к. активность выполняется повторно после доработки).
- `Result = reject` → терминал «Заявка отклонена» (45 раз). Пример: `08a60c66-22dd-5cf8-90dd-71ba3d53f349`.
Проверено: во всех 45 случаях `reject` — это **последнее** выполнение «Первичной проверки» в экземпляре, и непосредственно за ним идёт «Заявка отклонена» (без исключений).

### Развилка 2 — «Согласование руководителем» (manager)
Здесь обнаружено **четыре** исхода (в задании упомянуты только accept/return; reject и cancel — наблюдаемый факт, не гипотеза):
- `accept` (911) → «Проверка бюджета».
- `return` (174) → «Доработка заявки» (цикл, см. ниже).
- `reject` (18) → терминал «Заявка отклонена». Пример: `02bf4e3d-60b1-5713-9886-43fa49c67001`.
- `cancel` (26) → терминал «Заявка отменена». Пример: `00e3854b-efb6-59c7-ac6a-c85643843db1`.

Соответствие `Result → следующая активность` на этом шаге строго детерминировано и подтверждено `assert`-проверкой на всех вхождениях активности во всех 1000 экземплярах — исключений нет.

### Возврат (цикл доработки)
При `return` на «Согласование руководителем» наблюдается цикл:
Согласование руководителем → Доработка заявки (requester) → Первичная проверка → Согласование руководителем → …

- Один проход цикла — 174 экземпляра (прямой переход «Доработка заявки → Первичная проверка» встречается ровно 174 раза, совпадает с числом `return`).
- Из них у 18 экземпляров цикл повторяется **дважды подряд** (активность «Первичная проверка» и «Согласование руководителем» выполняются трижды с разными `TaskId`) — пример `009608ae-1567-584a-b67a-c7ec60ec587d`. Повторные выполнения не были отброшены как дубликаты (разные `ActivityId`/`TaskId` на каждом проходе), что соответствует указанию в `dataset_description.md`.
- После цикла (одного или двух) процесс всегда возвращается на магистраль: ни разу после «Доработки» не зафиксирован `reject` или `cancel` — во всех 174+21+18=... случаях выход из цикла идёт только через повторное `accept` на «Согласование руководителем» и дальше по магистрали. Это наблюдаемый факт по всем циклическим экземплярам в журнале, но с малым числом наблюдений для глубины >2 проходов — таких в журнале нет вовсе (гипотеза об ограничении на 2 возврата не подтверждена и не опровергнута, это пробел данных, а не установленное правило).

### Необязательная ветка — «Дополнительное согласование» (director)
Появляется между «Проверка бюджета» и «Исполнение закупки» в 209 из 911 случаев, дошедших до проверки бюджета (22,9%). Порог четко связан с суммой заявки:

- `Amount < 150 000` (702 случая) — доп. согласования **ни разу** не было (максимум в этой группе 149 743.41).
- `Amount ≥ 150 000` (209 случаев) — доп. согласование было **всегда** (минимум в этой группе 150 614.59).

Порог 150 000 подтверждён исчерпывающей проверкой (0 исключений с обеих сторон границы), это не статистическая тенденция, а детерминированное правило маршрутизации, выводимое из данных. Пример включения ветки: `01ae1813-1d99-5524-8f81-77ad5452c33e` (Amount = 216 508.25).
`Результат` на «Дополнительное согласование» во всех 209 случаях — `accept`; случаев отказа директора в журнале нет (пробел наблюдений, не доказательство отсутствия такой возможности в системе).

## 5. Факт vs гипотеза

**Установлено как факт** (проверено assert’ами на всём журнале, без исключений): набор активностей и ролей; единственный старт; три терминала; детерминированная маршрутизация по `Result` на «Первичной проверке» и «Согласовании руководителем»; строгий порог 150 000 для «Дополнительного согласования»; место вставки этой ветки (между «Проверкой бюджета» и «Исполнением закупки»); число и состав всех 8 вариантов.

**Остаётся гипотезой/допущением**, т.к. журнал не содержит внутренних определений шлюзов:
- Является ли условие именно `Amount` (а не коррелирующий с ним скрытый признак) — в данных нет других кандидатов на переменную с таким чистым разделением, поэтому гипотеза наиболее правдоподобна, но не доказана напрямую (нет поля «правило маршрутизации»).
- Ограничение на число циклов доработки (в данных максимум 2, но это может быть случайностью генерации, а не жёстким лимитом схемы).
- Возможность отказа на «Дополнительном согласовании» — в данных не встречается ни разу, отсутствие наблюдения не равно отсутствию возможности.
- Граф непосредственно следующих активностей (directly-follows) в принципе допускает больше поведения, чем 8 наблюдённых вариантов (например, теоретически — два независимых цикла с доп. согласованием после второго круга), но в журнале такое не зафиксировано; схема в разделе 6 это разбирает отдельно.

## 6. Автоматическая модель vs ручная (усложнённая часть)

Автоматическая модель построена здесь как частотный граф directly-follows (переходы между соседними активностями, см. `student_transitions.csv`) — по сути, это и есть основа ручной модели, т.к. все 12 переходов однозначны и воспроизводимы кодом.

Что граф DFG восстанавливает хорошо: все 12 рёбер соответствуют реальным, часто наблюдаемым переходам (минимальная частота ребра — 18), ложных рёбер не возникло.

Где DFG даёт больше свободы, чем показал журнал: сам по себе граф «Первичная проверка → Согласование руководителем → Проверка бюджета → Дополнительное согласование → Исполнение закупки» и «Согласование руководителем → Доработка заявки → Первичная проверка» формально допускает, например, прохождение цикла доработки **после** «Дополнительного согласования» и возврат к нему же, или смену «решения» по сумме при повторном проходе цикла — такие пути грамматически возможны в графе рёбер, но ни разу не встречаются среди 1000 реальных историй: во всех 21 случае с циклом **и** доп. согласованием доп. согласование происходит один раз и строго после последнего прохода «Проверки бюджета», а не до него и не повторно. Это — типичное ограничение representational bias графа «следующий-за»: он кодирует только парные соседства и теряет информацию «одного и того же проекта заявки», которую даёт полная таблица вариантов. Поэтому в отчёте в качестве окончательного свидетельства используется именно таблица из 8 вариантов (раздел 4), а граф — как компактная, но более широкая по допустимому поведению проекция.

Проверка автоматических выводов: каждое ребро графа и порог по `Amount` проверены `assert`-ами на полном журнале (0 исключений), а не оставлены на уровне «похоже на правду» — см. вывод `analysis.py`.

## 7. Ограничения метода

- Данные синтетические и полностью наблюдаемые (нет пропусков, нет параллелизма — каждое задание выполняется последовательно одним исполнителем), поэтому задача проще промышленного process mining, где бывают шум, параллельные ветки и неполные трассы.
- Малые частоты (18 случаев для V7 и V8) не позволяют статистически надёжно судить о поведении на границах (например, возможен ли третий цикл доработки) — выводы по ним качественные, подтверждены только примерами, а не статистикой.
- LLM использовался для ускорения написания кода анализа и формулировки первичных гипотез (объяснение полей, структура ветвлений); ни один вывод отчёта не принят без прогона `analysis.py` на исходном `students.csv`.
